# 跨设备进度同步：实施方案（计划稿）

> 目标：电脑上看到第 20 分钟，手机上打开能接着从第 20 分钟看。
>
> 现状：所有进度存在**本机 localStorage**，设备之间完全隔离。
> 本文档只做**方案设计与准备清单**，不含实现代码。

---

## 一、现状摸底

### 1.1 当前数据存在哪

全部在本机 `localStorage`，共 **17 个键**加动态进度键：

| 键名 | 内容 | 需要同步 |
|---|---|---|
| `viewingHistory` | 观看历史（含进度、集号、封面、剧集列表） | ✅ **核心** |
| `videoProgress_<url哈希>` | 单集精确进度 | ✅ **核心** |
| `favorites` | 收藏列表 | ✅ 应该同步 |
| `selectedAPIs` | 勾选的数据源 | ⭕ 可选 |
| `customAPIs` | 自定义源 | ⭕ 可选 |
| `episodesReversed` | 正序/倒序偏好 | ⭕ 可选 |
| `autoplayEnabled` / `playerObjectFit` | 播放偏好 | ⭕ 可选 |
| `yellowFilterEnabled` / `doubanEnabled` / `doubanApiMode` | 开关 | ❌ 不必 |
| `currentVideo*` / `currentEpisode*` | 播放页临时态 | ❌ 不必 |
| `hasInitializedDefaults` | 初始化标记 | ❌ 不必 |
| `passwordVerified` | 密码验证状态 | ❌ **绝不同步** |

### 1.2 同步的核心数据结构

`viewingHistory` 是一条数组，每条长这样（`player_utils.js:38-50`）：

```json
{
  "title": "沙丘2",
  "directVideoUrl": "https://.../index.m3u8",
  "url": "player.html?url=...&index=12&position=1234",
  "episodeIndex": 12,
  "sourceName": "非凡影视",
  "cover": "https://...",
  "timestamp": 1760000000000,
  "playbackPosition": 1234.5,
  "duration": 2832,
  "episodes": ["https://...", "..."],
  "episodeNames": ["第1集", "..."]
}
```

**关键问题：`episodes` 数组有几百条 URL，一条历史记录可能几十 KB。**
50 条历史全量上传 = **几 MB**，每个设备频繁同步会浪费流量。

### 1.3 同步的四个难点

| 难点 | 说明 | 影响 |
|---|---|---|
| **① 播放源会失效** | 采集站 URL 有时效，几天后打不开 | 同步过来也播不了，需重新搜源 |
| **② 无统一作品 ID** | 不同源同一部剧，`title` 可能差一个空格；`vod_id` 各源不同 | **匹配不准，会把两部片混在一起** |
| **③ 写冲突** | 电脑和手机同时看，谁覆盖谁 | 需要时间戳裁决 |
| **④ 数据量大** | `episodes` 数组冗余 | 流量浪费、同步慢 |

**难点 ② 是最致命的**——现有 `normalizeVodTitle()` 只去空白和标点，跨源匹配仍然很脆。

## 二、三种方案对比

### 方案 A：无账号，手动导出/导入

**做法**：复用已有的"配置导入导出"（`config_io.js`），把 `viewingHistory` 也打包进去，用户手动传文件。

| 优点 | 缺点 |
|---|---|
| 零后端、零成本 | 完全手动，不叫"同步" |
| 立即可用 | 每看一次都要导出导入，不现实 |
| 无隐私风险 | — |

**结论**：**只能算临时补丁**，不解决"自动同步"诉求。

---

### 方案 B：第三方云盘（WebDAV）

**做法**：把进度写成 JSON 文件，存到**用户自己的 WebDAV**（坚果云、Nextcloud、Alist 等）。

```
App 启动 → WebDAV GET progress.json → 合并 → 本地
播放中   → 每 60 秒 WebDAV PUT progress.json
```

| 优点 | 缺点 |
|---|---|
| **不用自己买服务器** | 需要用户有 WebDAV 账号（坚果云免费版就够） |
| 数据在用户自己手里，无隐私顾虑 | WebDAV 请求要走 Rust 转发（跨域） |
| 手机/电脑/电视都能接 | 并发写入可能冲突（需合并策略） |
| 实现量中等（~400 行 JS + Rust 透传） | 依赖第三方服务可用性 |

**成本**：0 元/月（坚果云免费 1G 够用几年）

**结论**：**性价比最高**。适合"就想两台设备同步"的个人场景。

---

### 方案 C：自建服务器（你的老笔记本 / 云函数）

**做法**：自己写一个小的同步 API。

```
POST /api/sync  { deviceId, token, history: [...] }
GET  /api/sync?since=<timestamp>
```

跑在：
- **老笔记本**（局域网内可用，出门在外不行）
- **云函数**（Vercel/Cloudflare Workers，免费额度够用）
- **VPS**（最灵活，要花钱）

| 优点 | 缺点 |
|---|---|
| 完全可控，想加什么功能都行 | **要自己维护** |
| 可以顺便做"账号体系" | 服务器挂了同步就断 |
| 数据格式自己定 | 有安全责任（要防数据泄露） |

**成本**：
- 云函数：0 元/月（免费额度内）
- 老笔记本：0 元，但**只能在家里的 WiFi 用**

**结论**：想长期做、想要多用户、想要账号体系 → 选这个。否则过重。

---

### 方案 D：不要账号，用"设备码 + 云函数"

**做法**：不注册账号，首次同步时生成一个**同步码**（如 `7K2M-9XQ4`），在两台设备输入同一个码即可。

```
生成码 → 上传进度到 <码>.json
另一设备输入码 → 拉取
```

| 优点 | 缺点 |
|---|---|
| **不需要注册/登录** | 码丢了就找不回 |
| 用户零门槛 | 安全性弱（码就是密码） |
| 可以完全匿名 | 不适合长期产品化 |

**结论**：**个人自用最省事**，比方案 B 体验更好（不用搞 WebDAV 账号）。

## 三、推荐路线

### 阶段一：本地"进度合并"地基（**必做，无依赖**）

不管最后用哪种云端，**先解决同步数据的正确性**。这一步纯本地，零风险。

| 任务 | 说明 |
|---|---|
| **1. 统一作品 ID** | 新增 `canonicalId` 字段：`normalize(片名) + 年份`，作为跨源唯一标识 |
| **2. 精简同步载荷** | `episodes` 只上传前 3 条用于识别，不上传全量 |
| **3. 合并函数** | `mergeHistory(local, remote)`：按 `canonicalId` 对齐，`timestamp` 新的胜出 |
| **4. 抽出同步层** | 新建 `sync_core.js`，提供 `exportSyncData()` / `importSyncData()` / `mergeSync()` |

**产出**：即使没有云端，也能做"手动导出导入"，且数据格式为云端做好准备。

---

### 阶段二：接入存储后端（**选一个**）

| 场景 | 选哪个 |
|---|---|
| 就想两台设备同步，不想折腾 | **方案 D**（同步码 + 免费云函数） |
| 已经有坚果云/Nextcloud | **方案 B**（WebDAV） |
| 想长期做，要多用户 | **方案 C**（自建） |

**我推荐方案 D**，理由：注册门槛最低、免费额度够用、不用用户操心 WebDAV 配置。

---

### 阶段三：体验打磨（可选）

| 任务 | 说明 |
|---|---|
| 播放中自动上报 | 每 60 秒或切后台时上报 |
| 冲突提示 | 两端都看过同一部但进度不同 → 选哪个 |
| 片源失效自动重搜 | 同步过来播不了 → 提示"换源" |
| 同步状态 UI | 显示"已同步 2 分钟前" |

## 六、风险与诚实的限制

| 风险 | 严重度 | 说明 |
|---|---|---|
| **跨源匹配不准** | 🔴 高 | 同一部剧在不同源名字有差异（"沙丘2" vs "沙丘2：第二部"），可能匹配失败或错配。**目前没有可靠的解决方案**，只能靠标题归一化 + 年份，准确率估计 70-85% |
| **同步过来播不了** | 🟡 中 | 采集站 URL 有时效，历史里的链接几天后就失效 |
| **无官方作品库** | 🟡 中 | 不像 TMDB/豆瓣那样有唯一 ID，这是架构层面缺失 |
| 并发写冲突 | 🟢 低 | 用时间戳裁决即可 |
| 隐私 | 🟢 低 | 若用方案 B/D，数据不进我的服务器 |

**最诚实的判断**：
> 进度同步本身**不难**（几百行代码）。
> 难的是**"怎么认定两台设备说的是同一部片"**——这个项目没有统一的影视 ID 体系，
> 只能靠标题猜，**必然有不准的情况**。
>
> 所以建议：**先做，但降低预期**。接受"偶尔对不上"，不要指望 100% 准确。
